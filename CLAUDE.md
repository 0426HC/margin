# Margin

Margin is a local AI study app. You drop in a course folder (PDFs, Word, PowerPoint, notes). Margin groups it by week, splits each week into **layers**, and a student learns one layer at a time: read a plain explanation, check it against the verbatim source, write it back in their own words, get specific feedback. Built by one student for their own use; it is also a portfolio piece, so code quality, design quality and the README matter as much as features.

## The study method (the goal behind every feature)
1. Start from the foundation underneath the course. Explain the basics a student is missing.
2. Driven by the student's confusion: "I don't get it" explains only that gap, one step simpler.
3. One layer at a time, each with a title and one big question, building on the last. Nothing is locked; any layer, any order.
4. The student writes each layer back in their own words. This is the step that makes it stick.
5. Feedback: specific fixes shown as "yours → fixed" in full sentences, then a cleaned-up version that keeps the student's wording, then one "so what" sentence. The verdict is for information only.
6. Short chunks, plain words, every name explained the first time, topic sections and tables (2x2 typologies as tables with an explanation in each cell). No story format; analogies only if they hold up.
7. Every named concept in the readings is covered (what it means, how it shows up, an example, why it matters), not just the big themes.
8. Never invent facts or pages. Everything is checkable against the student's own files.

Margin is not a flashcard, summary or quiz app. When a prompt, a screen or a rule conflicts with these eight points, the method wins.

## How Margin works
- **Import: code reads the files, Claude reads the course.** Code (`lib/import`) only extracts text, pages, headings and the author a file's properties name, cuts verbatim sections and ~180-word passages with file and page (indexed in SQLite FTS5), and sets aside exact copies (same bytes), and reads printed page numbers (`lib/import/printed-pages.ts`, `files.page_offset`). Everything else is AI (`lib/import/organize.ts`, prompts in `lib/ai/prompts/organize.ts`, written around goals and the reason for each rule): a quick look names the syllabus file, then one `organize` call (Opus) gets the full syllabus, the folder tree and each file's measured facts (type, pages, real words over the whole file, words per page, author, headings, first ~1,500 words) and returns the course's weeks (number, date, title in the syllabus's words, class / no-class / exam, what the syllabus says), the breaks between them, and every file's week, type (`lib/projects/file-kinds.ts`: reading, lecture, my-notes, syllabus, exam, optional), sure / check this, a one-line reason, and for a file the syllabus assigns in parts to two or more weeks each week's page range (`pages`, printed numbers), plus readings not found and files not in the syllabus. **Weeks follow the course's own numbering** (classes, lectures or weeks as the syllabus numbers them); an unnumbered break such as reading week sits between weeks and is never a week; folder numbers are used when they agree with the syllabus, and a genuine disagreement is marked check this with both sides; calendar weeks only when nothing is numbered. The student's folders are respected unless clearly wrong. Student notes are told from the professor's lecture material by author, writing style, whether a file mirrors a lecture, and folder names. Code checks the answer (every file once, weeks inside the course, course material has a week, breaks follow a listed week), retries once with the problems, and on a second failure leaves the files unlabelled with a message for the student to label. A good answer then gets the **final check** (`check` task, Opus low): one look over the whole result like a teaching assistant (week count vs folders and syllabus, empty or overloaded weeks, names or folders contradicting a label, syllabus items unaccounted for), answering only with changes (fixes, check-this marks, notes); code checks the changes the same way, sends them back once with the problems, and drops them if they still don't fit; if the check can't run, the first answer stands. It shows as an import progress step; breaks and its notes show on the plan screen ("What the final check noticed"). No fallback rules. **One file, different pages in different weeks** (`lib/projects/page-ranges.ts`): the file is stored and read once, its ranges are kept in `file_pages`, and every passage goes to the week whose range holds its page (narrowest range wins; pages no week is given stay with the file's folder week); exact copies with no different ranges are used once. Courses imported before this are checked once in the background (`page-ranges-check.ts`, `check` model) and moved passages are placed like new material. Weeks are stored in `course_weeks`; breaks and notes in the `course-map` ui_state note; `files.type` / `reason` / `needs_check` / `author` hold the labels (`category` and `role` follow from `type`; a null category means unlabelled). **Lecture material** (type `lecture`) is anything the professor posts for a lecture, whatever its format; it is course material (layers and the Lecture tab). Only `my-notes` is copied into the Lecture notes tab; a file that stops being my-notes takes its copy out (the student's own lines stay). The import route streams progress lines. Each week is a row in the `parts` table (historical name). A passage's week is `lib/layers/passage-weeks.ts`.
- **Layers** (`lib/layers`): the AI (`structure` task, Opus medium) reads the full text of every passage of a week, with the course name, the week's title and what the syllabus says, and proposes 2–5 layers; code validates (every passage in exactly one layer of its own week, at least 2 layers unless the week has under 1,500 words) and falls back to one layer per file (split to two when needed). The student edits the plan and approves it ("Looks good"). New files later go through "What's new" (`lib/updates`): code measures them and the same organizer labels them against the stored syllabus, the course's weeks and its files.
- **Course brain** (`lib/brain`): right after import (not waiting for approval) every course file is read in full in the background, current week first, one `brain` call (Sonnet) per file with every passage numbered (parts of ~30,000 words). It returns notes (concept, person, event, case, place, plus one reading note): name, other names, what, why it matters here, passage numbers, related. Code checks every number (one retry, then drops bad ones) and maps it to the real passage. "Other names" are only true alternative names or spellings for exactly the same thing (related things are links); code drops an other name that is another note's name in the same answer or is listed as related (`trueAliases`). Notes merge across files only when they are the same thing (`sameThing`: the same name, or each gives the other's name as an other name) (`brain_notes` + one `brain_mentions` row per file); brains read before this rule are checked once in the background (`names-check.ts`, `check` model, marked by migration 0023): the AI names the notes that merged different things or keep loose other names, code checks the answer against each note's own names and files (one retry), then trims and splits, each file's description going with its thing; links are rebuilt after every file from shared passages and named relations (`brain_links`). The queue is `brain_reads`; a heartbeat notices sleep, so a call cut off by sleep is retried at once. Update from folder reads new files; removed files take their places with them (`tidyBrain`). Progress: "Margin has read 4 of 12 weeks" in the course page bar, a book mark beside each read week, "Knows Weeks 1-4 so far" in Let's talk!.
- **Source**: the AI picks passage ids; code copies the text. **Explained** (`explainedSchema`, stored with `version: 2` and the big question): a 2-3 sentence summary, the big question, 3-6 sections each answering a sub-question (how and why), and the so what linked to the week and the course. No table of terms: every named concept, person, case or term is explained inside the section where it matters (what it is, a cited example, why it matters). Claude writes it as **streamed plain text** (`lib/layers/explained-text.ts`: `# Summary`, `## sub-question`, `# So what`), shown in the page as it arrives (`layer-progress.ts` carries the text so far). Then `explained-check.ts` checks it part by part and writes again only what failed, in one round side by side: a section citing a page that wasn't sent or citing nothing is rewritten alone (`fixSection`); a length outside its share rewrites only the longest (or shortest) sections; a brain note the readings discuss (2+ of the layer's passages, most discussed first, as many as the share holds: `requiredNotes`) that no cited passage of 18+ words names (`isExplained`: name, other name, plural, surname, or most key words of a descriptive name) gets one or two sentences added to the section where it matters (`explainMissing`). Then bad citations are stripped and lone citations folded in (also when showing any Explained). Only text with no usable shape is written again whole, once. The explanation gets about 4,000 words per week shared by source words (`explained-length.ts`); the prompt also gives words per section, set a little under the share because Claude runs about a fifth over. Writing never waits for the brain: it uses the notes the brain has, puts the layer's unread files first in the brain's queue (`wantBrainFiles`), and stores `conceptsChecked: false`; `checkLayerConcepts` adds what is missing once they are read. Layers written with the old Key concepts table were marked stale by migration 0024 and are written again when opened (the demo excepted); v1 Explained stays until refreshed. **Lecture tab**: written from the week's lecture files (numbers counted by code) plus the student's own lecture notes.
- **Background work** (`lib/layers/background.ts`): two lanes side by side. The brain lane: older courses' page-range check and other-names check, then the brain (files a layer being written needs first). The layer lane: layers the student is heading for (the one after an opened layer), then named-things checks the brain has caught up with, then after approval the remaining unwritten layers, current week first. A layer the student opens is never queued: `requestLayer` writes it at once at "now" priority (a layer already being written ahead is joined and promoted, `promoteLayer`). The engine pool (`lib/ai/queue.ts`) runs up to 5 calls, background calls at most 2, "now" calls first. Writing a layer stops only when nothing new arrives from Claude for 3 minutes while the student waits (`MARGIN_LAYER_IDLE_S`; the engine reports every chunk through `onActivity`). In-flight layers and priorities live on globalThis, because Next loads the worker and the routes as separate module copies. The queue is the database, so it survives restarts; it pauses at the usage limit and resumes alone. `MARGIN_BACKGROUND=off` disables it (browser tests do).
- **Course page** `/p/[id]`: tabs Layers, Let's talk!, Lecture notes, Exam room, Note to Self. **Layer workspace** `/p/[id]/l/[layerId]`: layer list, Explained | Lecture | Source, and the write-back with the tutor. While a layer is written only its content area waits (the explanation streams in under one status line); the layer list, back link, Escape and the course's other rooms (`LayerLinks`) stay usable, and leaving never stops the writing (the page's answer that follows it closes while the page is hidden and opens again when it is shown). While a layer loads, its route shows `LayerFrame` (the same panes, title, big question, tabs and write-back pane; the reading and write-back panes inert, the back link, layer list and rooms live; one status line) drawn from the course structure the course page or the previous layer remembered (`lib/layers/frame-peek.ts`; layer links are noted by a capture click listener in `LockInRoot`); the course page's zoom hands over as soon as its sheet has landed. Cmd+K jumps anywhere.
- **Let's talk!** and the Note to Self chat: `gatherCourse` (`lib/brain/ask.ts`) — the AI picks notes by meaning from the brain's index (`talk` model, task label `talk-pick`), code adds linked notes and sends their real passages (~25) with the reading notes; unread weeks fall back to FTS5 and the answer starts with "I haven't finished reading Week 9 yet, so this comes from a quick search."; the syllabus and optional readings are always word-searched. Sources collected by the Librarian, a Notepad. **Note to Self**: saved write-ups and quick notes, with its own chat. **Exam room**: sheet summary, practice sets, marking. **Agents** (Librarian, Explainer, Examiner, Connector, Quizzer) make documents from notes: a note naming a week, layer or reading (`lib/brain/scope.ts`) gets all of that material (up to 60,000 words) plus its brain notes; one naming material the course doesn't have gets one sentence and no AI call; otherwise `gatherCourse`. The prompt forbids padding with unrelated material. The Librarian is code only. The dining hall shows real `agent_tasks`.
- **Lock in**: one switch turns off everything decorative and uses the Graphite palette; includes a focus timer.
- **Demo**: a read-only public-domain course (Federalist Papers), pre-generated with the real engine (`demo/`, `npm run demo:build`: import, the brain reads every file, then every layer is written; the seed carries the brain's notes, mentions, links and reads). Builds (`next build`) get an empty `MARGIN_DATA_DIR` of their own, never `.data`. Its structure is read-only; write-backs, Let's talk! and Note to Self work in it. README screenshots: `README_SHOTS=1 npx playwright test -c playwright.readme.config.ts` (the real engine and a throwaway data folder, from the demo and its own sample folder; writes `docs/readme/*.jpg`). The README's extra screenshots (home, new course, agents' panel, Lecture notes) and the raw clips behind its GIFs come from `README_MEDIA=1 npx playwright test -c playwright.readme-media.config.ts` (demo course only, real engine); `FFMPEG=/path/to/ffmpeg node scripts/readme-gifs.mjs` turns the clips into `docs/readme/*.gif` (each under 5 MB; ffmpeg is never an app dependency). `/style-guide` is the living design reference. Local-only experiments stay out of git (listed in `.git/info/exclude`), never part of the study app.
- Deleting is permanent and complete (rows and stored files); confirmations use Margin's own `<dialog>`, never browser alerts.

## AI engine
- Runs through the official Claude Code CLI in headless mode (`claude -p`) on the creator's laptop and plan. No API key. Never use the Agent SDK with subscription credentials, and never read, copy or store Claude OAuth tokens: the app only spawns the `claude` binary.
- One interface, `lib/ai/engine.ts`: `ClaudeCodeEngine` (default), `AnthropicApiEngine` stub, fake engine (`MARGIN_ENGINE=fake`, tests). Flags and limits are in `lib/ai/claude-code-engine.ts` and `lib/ai/queue.ts`; the prompt goes on stdin and the cwd is an empty temp folder so no project files are read.
- Model and effort per task are in `lib/ai/config.ts` (override with `MARGIN_MODEL_<TASK>` / `MARGIN_EFFORT_<TASK>`). Tasks: review, organize, structure, lecture, exam, request (Opus medium), explain, check (Opus low), talk, notes, brain (Sonnet). Requests carry a priority ("now" or "background") and an `onActivity` callback. All prompts are typed functions in `lib/ai/prompts/*.ts`; structured outputs are Zod-validated.
- Retrieval is done by the app (the brain's notes, then FTS5 BM25 with common words left out), never by AI tools; the AI only picks note ids from a list. The AI returns numbers; code copies the real text. Never trust an AI citation without checking it against what was sent.
- Never wait forever: the engine's idle and whole-call limits and a layer's quiet limit are env-tunable. Each call logs one line, never the prompt.

## Tech stack
Next.js (App Router, read `node_modules/next/dist/docs/` before using an API; see AGENTS.md) + TypeScript strict + React; Tailwind v4 with tokens in `app/styles/tokens.css`; Motion; Lenis (home page only); SQLite via better-sqlite3 + Drizzle (hand-written migrations in `lib/db/migrations`); pdfjs-dist, mammoth, jszip; Zod at every AI and API boundary. Data lives in `./.data` (dev) or `MARGIN_DATA_DIR`. The Mac app (`scripts/mac`, `docs/mac-app.md`) serves a production build in a Chrome app window with its own profile.

Commands: `npm run typecheck`, `npm run lint`, `npm test` (Vitest), `E2E_PROD=1 npx playwright test` (browser tests on the production build), `scripts/check-clean-build.sh` (builds the committed `public` branch from `git archive` in a fresh temporary folder with an empty data folder, exactly as Update Margin does). Structured answers from Claude have stray `\"` escaping removed at the engine (`unescapeQuotes`).

## Design rules
- **Fonts**: Bricolage Grotesque (display), Literata (reading, ~65ch), Courier Prime (labels, page markers, citations), served from `app/fonts` (`app/styles/fonts.css`), never downloaded at build time. Sentence case, no tracked all-caps.
- **Normal palette (midnight + plum)**: desk `#111827`, panel `#161f31`, paper `#edf0f6`, ink `#131b2d`, accent `#233f8f`, plum `#d38ae0` on the desk / `#7d2c92` on paper (saved only), coral `#f07f73` (errors only).
- **Lock in (Graphite)**: bg `#0e0f11`, surfaces `#16181b`, borders `#26292e`, text `#ececee`, quiet `#8b8f97`, accents `#d38ae0` / `#6b2c7e`, reading `#1b1d21` on `#e3e4e8`.
- No green, yellow or gold anywhere. No emoji as icons, gradient text, glowing pills, identical rounded-card grids, "AI" badges or stock phrases.
- The header never has a background; content fades under it.
- Citations and file-and-page markers live in a left margin gutter beside the text.
- The course page's week scenes and opening move on CSS scroll timelines (`view-timeline`, ranges from `scrollRange` in `components/cinematic/geometry.ts`), so the compositor plays them with the scroll; never drive them from script. `PERF=1 E2E_PROD=1 npx playwright test perf-overview` measures the scroll (see the spec's header).
- Cinematic outside, calm inside: the home and course pages carry the expressive motion; the layer workspace stays quiet (150–300ms, strong ease-out, nothing animates on keyboard actions). Transform and opacity only. Reduced motion is always respected.
- Laptop-first (1280–1600px); nothing breaks at 1024px. Copy is plain, warm and specific; buttons say what happens; errors say what went wrong and how to fix it.

## Safety rules
- Never read or edit outside `~/Projects/margin` (except `~/.nvm` and temp folders).
- No `git push`, `sudo`, `curl` or `wget`.
- Tests always use the fake engine (`MARGIN_ENGINE=fake`) and a separate temporary data folder, never the real `.data`. A layer titled "(fake: slow)" streams its Explained over about ten seconds, for the browser tests of a layer being written. The fake engine's stand-in for reading a folder (`cannedJson` in `lib/ai/canned.ts`) is for tests only; tests of the import's own logic play Claude with scripted answers (`tests/unit/helpers/organizer.ts`, `tests/fixtures/varied-courses.ts`).
- Never commit course files, `.data`, backups, `.mac-app`, `private/` or audio files. Tests use made-up text only.
- The README and every committed file stay free of the owner's personal details, private experiments and plans (the full list is in `private/how-margin-decides.md`).
- Commits go on the `public` branch.
- Commit messages carry no `Co-Authored-By` or any other attribution, session or trailer lines, whatever other tooling suggests. Author and committer are `Margin <298624512+0426HC@users.noreply.github.com>`.

## How to work on Margin
- When changing something, replace the old way completely. Never add a new rule or workaround on top of an old one, and delete code that is no longer used.
- Update this file at the end of every round so it always matches the code. Where docs and code disagree, the code is the truth.
- Use one progress file per round, `docs/round-progress.md`, and delete it when the round is finished.
- Think before coding, keep changes surgical, and call a task done only when typecheck, unit tests and the production browser tests pass (plus a screenshot looked at after UI work), and, after committing, `scripts/check-clean-build.sh` passes. That check catches committed code that needs an uncommitted file (untracked, in `.gitignore` or `.git/info/exclude`) or the network; fix it in the committed code, never by committing anything private. Keep `README.md` current.

## Known issues
- The remaining findings in `private/how-margin-decides.md` section 9 (Explained runs about a quarter over its share once missing concepts are added, and a week's 4,000 words can't explain every name the brain lists, so the checklist holds the most discussed; Source only shows what the AI picks; the brain merges notes by name, so two different things with one name become one note; a thing two files name differently, where only one side gives the other name, stays as two notes).
- Adding a new syllabus through "What's new" does not re-read the course's weeks; import the course again for that.
- "What's new" doesn't split a newly added file's pages between weeks; import the course again for that.
- The course page's week marks update on reload; the top bar line updates live.
